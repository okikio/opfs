# Protocol, streaming, encryption and archive planning findings

Read-only review of `/Users/okikio/Other/Code/opfs` at consolidated source `1496733`; researched 4 November 2026. Proposed contracts below are design work, not existing exports. No repository files changed and no provider operations executed.

## Existing reusable owners and the gaps

The project already has native object operations, ranged streaming GET, streamed replacement PUT, pagination, conditional writes/copies, multipart S3 and staged Azure blocks, Web Fetch request policy, exact cancellation/cleanup ownership, bounded byte chunking, and separate client/driver/adapter responsibilities. Reuse them. `src/driver/object.ts` is the contract owner; `src/request.ts` already refuses automatic retry when `replayable:false`. S3 exposes create/upload/complete/abort multipart operations. Azure block staging is currently private. Neither path exposes a durable transfer checkpoint or a common restart-after-process-death API.

Important new seam: `ObjectGetOptionsType` currently accepts offset, length and signal, but no revision/If-Match condition. A metadata request followed by unrelated range requests cannot establish one immutable remote archive. Add an explicit revision-pinned byte source, with source length, identity/revision and range-open operation. Implement ETag or provider-generation selection in each protocol client, then expose the seam through drivers/adapters. A backend that cannot pin must require immutable content identity, a caller-owned stable snapshot, or a bounded local spool; never silently mix revisions. Keep provider revision semantics distinguishable rather than pretending every ETag is a cryptographic content hash.

The object backend contract requires mutation methods. Upload-only protocols and read-only archive/CID views must not be misreported as full writable object/filesystem drivers. First add truthful read-only capability admission (mutations fail preflight before reading source or obtaining credentials), or expose them through their narrower independently useful API until that exists.

## GCS is the first missing cloud vertical slice

Implement a native GCS JSON API client in an explicit subpath, then `driver/gcs` and `adapter/gcs` composed through the existing object adapter. Authentication stays an injected access-token supplier; the application owns ADC, service-account signing, federation and refresh policy. Keep GCS generation/metageneration and rewrite/compose semantics in the client. Generic object receipts may carry the generation as provider revision but must not conflate it with an ETag.

GCS upload has a session URI and server-confirmed offset; ordinary PUT success/retry is insufficient. Nonfinal chunks have a provider alignment constraint (256 KiB multiple). On a lost acknowledgement, query session status and continue after confirmed bytes. A session URI grants upload authority, expires after a week, and belongs in protected checkpoint storage, not logs. Source identity must remain fixed across resume. [GCS resumable procedure](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads), [session authority and expiry](https://docs.cloud.google.com/storage/docs/resumable-uploads).

Pin downloads with generation selection or request preconditions. GCS supports ranged object retrieval and explicit generation selection. Reject unexpected full-body responses, inconsistent lengths or revision changes before combining range data. [Objects.get](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/get), [preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions).

## Transfer/resume contract

Propose a transfer module above protocol clients, not a new persistence engine. Its source is either an offset-reopenable immutable source or an explicit durable spool. A one-shot ReadableStream supports one attempt; it cannot honestly promise recovery across process death. Destination session operations are protocol-specific create/query/write/finish/cancel, surfaced through small capabilities. A unified coordinator may order them but must retain native offset, part-list and commit differences.

Checkpoint schema needs: schema/format/client compatibility versions; logical transfer and attempt IDs; source identity/revision/length; destination endpoint/key/precondition; protocol/version; acknowledged offset or parts with receipts/checksums; transform/framing version; committed publication receipt; and session expiry. Secret session material and keys are separate protected references. The caller supplies atomic checkpoint storage and source reopening. Progress is observation; checkpoint and terminal result are authority. Persist after destination acknowledgement, reconcile after restart, then advance. Unknown final publication is its own state; a later HEAD alone cannot attribute another writer's object to this transfer.

Pause stops dispatch and retains resumable state, abort stops current work, terminate explicitly discards the session, and dispose releases owned resources. Do not reuse one abort action for all four. A per-session single writer or compare-and-swap/lease prevents two resumes racing. Lost chunk acknowledgement must query provider state; blindly retrying mutating requests is unsafe even when bytes are buffered.

For tus 1.0, implement HEAD offset and PATCH offset admission first, then advertised creation, expiration, termination, checksum and concatenation extensions. No generic read/list/delete semantics can be inferred from a tus upload endpoint. [tus specification](https://tus.io/protocols/resumable-upload).

Keep the IETF protocol separate: as of this review it is active Internet-Draft `draft-ietf-httpbis-resumable-upload-15` (2 November 2026), draft interop version 10. It uses different headers and state rules and does not permit arbitrary parallel appends. It is not the tus 1.0 wire format. Pin the draft version and keep experimental until interoperability proof. [Draft 15](https://datatracker.ietf.org/doc/html/draft-ietf-httpbis-resumable-upload-15).

Fetch does not deliver general informational responses to application JavaScript. Therefore transparent early discovery via HTTPbis 104 cannot be promised from portable Fetch. Prefer explicit configured endpoints/creation with a final-response upload identity; add an injected advanced transport if interim-response discovery is necessary. [Fetch HTTP-network-fetch algorithm](https://fetch.spec.whatwg.org/#http-network-fetch).

## Encryption and archive composition

Keep TLS, provider-managed encryption (including KMS/customer-supplied-key options), client-side encrypted storage, and interoperable encrypted archive formats as distinct capabilities. Plain storage remains the default; encryption is explicit. An encrypted layer needs its own content-address/revision implications and must expose which metadata leaks (names, sizes, access patterns).

Web Crypto encrypt/decrypt accepts complete BufferSource messages, not a streaming AEAD object. Use built-in AES-GCM on bounded authenticated frames only after specifying a versioned file format: per-file key/nonce domain, unique nonce per key and frame across retries, authenticated index/file identity/format fields, authenticated final length/end marker, and independent frame verification before plaintext release. Bind frames against reorder, cross-file substitution and truncation. Do not describe a TransformStream wrapper around whole-file encrypt() as bounded streaming. New framing requires independent crypto review and published test vectors; do not implement block primitives. Keys remain caller-owned and absent from checkpoints/logs. [WebCrypto API](https://www.w3.org/TR/webcrypto-1/), [NIST GCM](https://csrc.nist.gov/pubs/sp/800/38/d/final).

Resume encrypted/compressed uploads in encoded-byte coordinates. Either retain exact encoded chunks durably or reopen a fixed source and reproduce bytes with the same framing parameters. A compression stream has hidden state and cannot start at an arbitrary plaintext offset. Retry from a stored restart boundary, recompute from the start with a stated cost, or spool encoded output. A new attempt must not reuse a nonce for changed plaintext. Encrypted ranges decrypt whole containing frames; report physical read amplification.

ZIP preview should be an independently useful read-only archive view above the revision-pinned byte source. Start with single-volume ZIP/ZIP64, stored and deflate methods. Read bounded tail metadata, validate central-directory/local-header relationships and safe integer/BigInt bounds, then fetch only the selected compressed member extent. Define duplicate-name, encoding, symlink and path-normalization behavior before projecting file paths. Stream member output with byte, ratio, entry-count, recursion, directory-size and CPU/time budgets. Check CRC/size; a prefix preview cannot claim full-member integrity before completion. Deflate member seeking may require decompression from its beginning. Initial ZIP modification is rewrite-to-new-archive and publish, not in-place arbitrary updates. [ZIP APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT).

CompressionStream/DecompressionStream provide codec streams, not ZIP directory parsing. Probe codec support per runtime; standard text alone does not establish installed-runtime availability. Gzip, deflate and deflate-raw are distinct wrappers. Additional codecs need an approved implementation seam, not accidental dependencies. [Compression Standard](https://compression.spec.whatwg.org/).

Encrypted ZIP is separate interoperability work. WinZip AE-1/AE-2 specifies its own key derivation/counter/authentication construction; a custom AES-GCM wrapper is not that format. Legacy encrypted formats may be read-only, explicitly weak compatibility and disabled by default. Do not promise encrypted metadata preview without the format's key. [WinZip AES format](https://www.winzip.com/en/support/aes-encryption/).

The reviewed Deno standard crypto source accepts iterable/async-iterable digest input and uses bundled WASM where native WebCrypto is insufficient. That is a candidate for incremental integrity with a pinned approved version and lifecycle tests, not a claim that native digest itself streams. No current ZIP API was verified in Deno std; do not invent `@std/archive` support. [Deno std crypto source](https://raw.githubusercontent.com/denoland/std/main/crypto/crypto.ts).

## Sequence and proof gates

1. Add truthful readonly/revision-pinned byte source and replayable source contracts; fixtures prove revision change, malformed ranges, byte budgets, cancellation and cleanup. Preserve existing object facade tests.
2. Deliver GCS normal CRUD/list/range/generation/preconditions vertically; then native resumable lifecycle. Protocol fixtures plus an opt-in ephemeral real GCS bucket test; emulator evidence cannot certify IAM, quotas or resumable parity.
3. Coordinator with checkpoint store + GCS/tus session bindings, then persistent S3 multipart/Azure block bindings. Tests kill after write/before checkpoint and after checkpoint, drop every acknowledgement, alter source/config/schema, expire sessions, race resumes, exhaust quota and fail cleanup. Verify final receipt/bytes, never progress alone.
4. ZIP read-only view over local and pinned cloud sources. Golden external archives and differential checks; ZIP64 boundaries, data descriptors, duplicates, malformed offsets, bombs, CRC failures, encrypted/unsupported cases, partial-preview labeling, slow consumers and nested quotas.
5. Framed encryption with reviewed format and crypto vectors; tamper/reorder/truncate/key/nonce tests and restart at every frame boundary. Compose ZIP->encrypt->GCS and reverse preview, then show exact cost and metadata leakage. Add interoperable vault formats as separate format modules after their own review.
6. Clean installed consumers per supported runtime; root import safety and optional-module exclusion; serial static gates in isolated CI, portable runtime tests locally with --no-check; memory/queue/part/concurrency bounds and truthful performance reports.

A useful cross-format flow is: immutable source -> selected archive member -> bounded decoder -> optional framed encryption -> destination transfer. A manifest records source revision, input/output format/profile, selected member, transforms and output receipt. Exporting ciphertext as bytes is different from decrypting; extract/repack/transcode require explicit operation choices. Cross-provider rename remains copy then conditional delete and never claims distributed atomicity.
