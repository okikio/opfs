# OPFS storage expansion plan

Updated: 5 November 2026. Source baseline: `14967334aee6b0f1815eecc1437fa9f174b97bb5`, branch `codex/release-2026-10-06`.

This is a proposed implementation program for the OPFS maintainer and engineers adding integrations. No provider, parser, encryption format, upload server, dependency, or public export is implemented by this document. Work should continue on the consolidated branch and existing PR when implementation is authorized. Planning artifacts are local and ignored; a fresh clone will not contain this directory.

The objective is broad, usable storage coverage with truthful capabilities: callers can select a storage location, inspect what it actually supports, stream data to it, recover interrupted transfers when possible, and read selected archive entries without downloading everything when the source permits it. A catalog record is an item to account for, not automatically a new driver or a claim of support.

Start with [README.md](README.md) for the decision summary. The revised [extension contract](EXTENSIONS.md), [preview model](PREVIEW.md), and [engineering gates](ENGINEERING.md) are part of this plan and refine its original waves. The 136 focused archive/encryption profiles and 14 implementation comparisons remain distinct from the unchanged 895-record catalog. [RESEARCH.md](RESEARCH.md) records the new sources, reuse decisions and review limits.

Start with the implementation sequence below. Use `routing.json` to find the disposition of every catalog ID, and `routing.csv` for filtering. Read `protocol-research.md` for protocol details and primary sources. The routing is provisional architectural triage. Its `delivery_wave` refers to the implementation table below; its separate `discovery_phase` preserves the coarser research grouping and does not set implementation priority. General behaviors routed to wave8 may need earlier use-case-specific work in waves0–4; each row is a primary owner, not every dependency. It preserves all records and uncertainties; it is not a provider certification table.

## What exists and what the catalog adds

The current source has file, record and object driver families; reusable adapters for those families; 16 concrete backend integrations; independent S3 and Azure clients; and reverse KV and unstorage bridges. There are 57 public subpaths including the root. `driver/host`, `driver/local`, `driver/generation` and writable support are internal contracts/mechanics, not additional cloud services. Source files and exports establish this inventory; they do not establish arbitrary compatible-provider or production-deployment support.

The supplied checkpoint has 895 unique catalog records: 453 concrete targets, 97 access protocols/APIs, 130 storage behaviors, 56 optional views, 70 tools, and 89 references. The original planning edition compared all 346 files in its source snapshot byte for byte with this unchanged source baseline. Its historical tus checkpoint is expressly outside that source lineage; no tus implementation is assumed present here.

The architecture already separates client, driver, adapter, filesystem and bridge. Keep it. A protocol client owns messages and acknowledgements; a driver owns backend mechanics, limits and resources; an adapter projects that driver into filesystem operations; `FileSystemType` owns paths and portable fallbacks. A reverse bridge implements a real consumer contract over an existing filesystem. Metadata declaring a direction is not a bridge.

Three gaps block reliable composition:

1. `ObjectGetOptionsType` currently has range and cancellation options but no immutable version or conditional revision binding. Multiple range reads can otherwise mix generations of a changing remote ZIP.
2. `AdapterType` currently requires write/delete/directory mutation methods. Read-only gateways and archive views need explicit mutation admission and truthful capabilities, not methods that appear writable until they fail after reading an input stream.
3. Multipart streaming exists, but durable restart/resume is a separate contract. S3 public multipart methods and Azure internal block staging do not by themselves persist a checkpoint, reopen a source, reconcile remote state or prove recovery after process death.

## A representative workflow

A developer wants a user to upload a large ZIP into GCS, optionally encrypted by the application, close the app, resume later, then preview one member. The user chooses a destination and protection mode, sees whether restartable upload and partial preview are available, starts the transfer, and can pause, resume or cancel. A source mismatch, expired upload or changed object produces a specific recoverable result rather than an apparently successful damaged file.

The system first admits capabilities and limits without consuming the source. A replayable source identifies the exact bytes and can reopen at a committed offset. The optional encryption layer emits reproducible authenticated segments for this attempt. The transfer owner creates a provider-specific session and saves the checkpoint only after remote acknowledgement. After restart it loads the checkpoint, validates source and destination identity, asks the provider what it retained, and resumes from the reconciled boundary. It verifies the final commit receipt before reporting completion.

For preview, a revision-bound range source reads ZIP directory records and only the selected compressed member. If encrypted, it maps those reads to complete authenticated ciphertext segments before exposing decrypted bytes. The preview consumer gets bytes plus integrity status; UI rendering and media decoding remain application responsibilities. Whole-file completion, one authenticated segment, a CRC check, and provider retention are different facts.

## Module and ownership decisions

“Submodules” means explicit package subpath exports, following the current package, rather than Git submodules. Keep one source tree and release unit initially. Add separate packages only for a real independent release cadence or heavy host requirement; do not split simply because there are hundreds of catalog names.

| Proposed surface | Responsibility | Composition rule |
| --- | --- | --- |
| `@okikio/opfs/gcs`, `/webdav`, `/swift`, `/b2`, `/tus` | Independently useful protocol clients | Own authentication seams, messages, native pagination, versions, sessions and errors; these exports do not exist yet. |
| `/driver/<backend>` | Configured native backend | Reuse file/record/object families when semantics fit; retain stronger native methods. |
| `/adapter/<backend>` | Convenience composition | Reuse generic translation; add backend-specific translation only for actual differences. |
| `/source` | Proposed revision-bound byte source and replay contract | Serve one addressable byte object without pretending it has a directory or mutation API. |
| `/transfer` | Bounded copy and transfer session lifecycle | Consume explicit source and destination capabilities; keep each provider's chunk/commit protocol below it. |
| `/archive/zip`, `/archive/tar` | Container inspection/read/write operations | Consume byte sources/sinks, expose entries and streams; do not connect to storage themselves. |
| `/view/zip`, `/view/tar` | Read-only filesystem projection | Optional projection over archive APIs after read-only admission is defined. |
| `/crypto` | Optional content encryption/decryption and format metadata | Separate payload protection from TLS, provider encryption and vault namespace formats. |
| `/profile/<service>` | Validated configuration/constraints for a shared protocol | Export only if it adds useful defaults or policy; otherwise use documented configuration. |
| `/bridge/<ecosystem>` | Existing filesystem consumed by another ecosystem | Implement the actual external contract, including failure and lifecycle semantics. |

Importing root or a client must not import every integration or start network, worker, wallet, credential discovery or database work. Maintain matching intentional exports in Deno/npm packaging; test the built package's dependency graph. Do not add a central eager provider registry. A generated metadata-only catalog may help discovery, but it must not load constructors.

All new API names in this plan are proposals. Confirm the naming against current exports before implementation; do not paste speculative calls into consumer docs as working examples.

### Read-only, revisions and native data models

Introduce an explicit read-only admission model shared by inspection and planning. Mutation must fail before source acquisition or provider effects. Update facade fallbacks, writable handles, append/update, recursive copy/move and destination admission together; do not scatter casts around required write methods. Existing writable adapters retain their behavior. Add negative compile fixtures and runtime tests for the new public contract.

Define a bounded sequential byte source with cancellation and explicit disposal/ownership first. Known size, immutable identity, range reads and reopen/replay are separate declared refinements; an unknown-size upload source must not invent them. The revision-bound random-access refinement requires size, identity and range reads. Identity distinguishes an immutable provider generation/version from a weak ETag, last-modified timestamp, or a bare URL. Bind every dependent request to the same version or strong precondition. If that is impossible, explicitly stage a bounded/spooled snapshot or refuse provider-verified stable random-access claims. An explicitly accepted caller assertion of stability is a weaker evidence mode: label the assumption and mutation risk, and never promote it to provider-bound snapshot consistency. Validate actual `Content-Range`, body extent, encodings and revision responses. An ignored Range response must not silently trigger an unbounded download.

Object drivers should preserve provider-native revision tokens as opaque strings, including GCS generations that must not be coerced through an unsafe number. Do not assume GCS generation, an S3 ETag and Azure conditions are interchangeable. Versioned/conditional reads and deletes need operation-specific contracts; deletion races are not solved by the current unconditioned `delete(key)` signature. The current object adapter derives replacement `ifMatch` from `previous.etag`. Before reusing that adapter for native GCS, extend its precondition handoff to carry a discriminated provider revision/generation, and translate it to the actual GCS generation condition. Never put a generation into the ETag field to satisfy the existing shape. Retain S3/Azure ETag behavior and prove both paths with conflict tests.

ID-based drives, append-only logs, SQL/query systems and content-addressed stores need their own native capabilities where the three existing families do not fit. A file projection may add a separately versioned manifest or naming index, with explicit authority and transaction rules. It must not advertise native directories, atomic rename, arbitrary overwrite, query transactions or deletion when the underlying system lacks them.

Prefer platform Fetch, Web Streams, WebCrypto, URL, TextEncoder/Decoder and compression APIs; then applicable `@std/*`; then verified published personal `@okikio/*` libraries and the current utility workspace. Existing repository dependencies keep their existing owners. This plan adds no dependency and does not replace Zod or existing test infrastructure.

| Candidate | Inspected evidence and proposed use | Boundary |
| --- | --- | --- |

| `@std/bytes`, `/encoding`, `/streams`, `/xml`, `/path`, `/async` | Already resolved by this repository; use relevant exported operations. | Pin through existing lock/task policy; do not install all siblings. |

Do not write AES, SSH cryptography, password KDFs or a decompressor from scratch merely to avoid a dependency. Implement protocol messages and container framing where they can be bounded and tested; use established primitives. A missing primitive becomes an explicit blocked capability, optional injected codec/client, or approval decision. No new package publication is authorized by planning.

## GCP implementation slice

GCP support should begin with native Google Cloud Storage, not just the GCS XML/S3-compatible access path. The native API is needed for generation conditions and native resumable sessions. Compatibility access remains a separately tested route with its own limitations.

1. Implement an independent GCS client for object metadata/media reads, paginated prefix/delimiter listing, upload, generation-qualified reads, preconditioned write/delete, and server-side rewrite/copy continuation. Start with caller-supplied access-token/authorization or delegated request capability; automatic ADC, metadata-server discovery, IAM provisioning and OAuth UI remain explicit optional owners.
2. Implement the GCS object driver and reuse the object adapter. Retain generations, metagenerations, CRC32C, object metadata, request identity and operation receipts. Never treat a later HEAD as attribution of an earlier uncertain commit. Folder/HNS-specific moves require a separate capability/profile; generic object copy/remove remains explicitly weaker.
3. Implement native resumable upload: session initiation, status query, acknowledged Range reconciliation, legal chunk alignment, zero-byte/final upload cases, unknown-size streams and session expiry. Treat session URIs as bearer secrets. A failed final response can mean unknown publication, not a safe retry.
4. Add browser/Worker and server fixtures: token refresh during a session, denied CORS, forbidden operations, conditional conflicts, overwritten sources, checksum mismatch, interrupted acknowledgement and session expiration. Use an emulator for deterministic fixtures where useful, but require isolated real GCS evidence for advertised service behavior.
5. Add Firebase Storage as a separate authorization/rules/emulator integration. Do not equate Firebase browser authorization with a GCS OAuth service account. Google Drive is a later ID-based drive client, including export semantics for Workspace documents. Filestore/Managed Lustre/NetApp services use an explicitly configured host mount route first; disk products need attachment and a filesystem, not an object adapter.

Profiles for archive classes, Rapid-specific services and cache products require current per-product capability validation. Their catalog presence does not imply generic GCS CRUD or immediate read availability.

## Streaming, resume and transfer contracts

The common seam is lifecycle, not a universal chunk algorithm. S3 multipart upload, Azure block lists, GCS contiguous session offsets, tus offsets and content-addressed publication have different commit and cleanup rules. Each session reports its native limits and supported resume/parallelism behavior.

A proposed transfer session has explicit start/query/write-or-advance/finalize/pause/cancel/dispose operations as appropriate to the backend. A serializable checkpoint contains a schema version, protocol/profile version, endpoint/account/destination identity, upload/session handle, source identity/size/revision, acknowledged ranges/parts and validators, transform/encryption parameters, preconditions and expiration. Credentials and encryption key material are separate from ordinary metadata. A store that retains a secret session URL must be treated as secret storage, not a log.

Checkpoint storage is injected and borrowed. Its save/replace must be atomic for the supported deployment. Single-writer ownership or compare-and-swap plus fencing is required if multiple processes can resume the same transfer. Do not imply an in-process lock provides distributed exclusion. This is library checkpoint recovery, not a new durable workflow engine.

Raw ReadableStreams are one-shot. A resumable source must reopen the exact bytes at a validated position: Blob slices, revision-pinned remote ranges, stable local files, or an explicitly owned spool. Local filename/mtime/size alone does not prove identity. A changed source rejects resume. Spooling has a quota, lifetime, cleanup record and an application-selected persistent location if recovery must survive process death. Compression/encryption may require replay from a transform boundary or exact persisted output; plaintext and transmitted-byte offsets are not interchangeable.

Use explicit states such as active, paused, completed, cancelled, expired and outcome-unknown. Pausing may retain remote state; cancellation requests remote cleanup; disposal releases local handles. Some providers cannot delete staged state immediately. Failed cleanup remains inspectable, with a finite deadline, without hiding the original failure. Progress is observation and includes acknowledged versus read/sent bytes.

For tus 1.0, implement the core protocol and creation first, then capability-negotiated creation-with-upload, expiration, checksum, termination, deferred length and concatenation. Offset conflicts require HEAD reconciliation. Checksums cover the exact protocol bytes. Do not advertise extensions based on the provider brand. Tus is an upload client/session capability; a tus server does not automatically supply listing, read, delete or filesystem namespaces. Add an explicitly configured discovery/read owner if a service offers those APIs.

A separately optional tus server bridge may expose an existing filesystem, but it needs upload metadata storage, offset fencing, retention, authorization and final-publication semantics. It is its own delivery slice, with independent server conformance tests. Browser client support is not evidence of server support.

HTTPbis resumable upload is a different evolving protocol, currently draft-15 with interop version 10 in the inspected source. Pin that draft in an experimental module; do not label it tus or an RFC. Fetch hides informational responses, so portable clients cannot assume they can observe the draft's 104 upload discovery response. Use an explicit final-response creation route when supported, or a separately injected transport with the required capability. Recheck draft status before implementation.

For downloads, persist destination revision/extent only after actual writes, verify the same remote version on continuation, and reconcile a partially written destination. A transfer between two stores has no general distributed transaction. Prefer writing to a private destination, verifying, publishing conditionally, then deleting the source only for an explicitly requested move. Keep the source if destination publication is uncertain. Never promise atomic cross-provider move.

## ZIP preview, archive writing and format composition

Implement a byte-level ZIP parser and entry reader independently of the filesystem view. Baseline support: single-disk ZIP, stored and raw-DEFLATE members, UTF-8 names and explicit legacy-name policy, data descriptors, CRC32 and ZIP64 with checked integer arithmetic. Refuse unsafe conversion of 64-bit values to JS numbers. Do not claim all ZIP methods because two methods work.

For seekable sources, locate the end directory records with bounded tail requests, load/index the central directory within explicit byte/entry limits, validate offsets and local headers, then fetch/decompress the chosen entry. Pin all reads to one object version. Stored members permit direct member-range mapping; deflated members generally need decompression from their start unless a real index exists. “Preview one member” is not “random access to every decompressed byte.”

For sequential sources, allow entry scanning with documented limits or spool under explicit policy. Stream ZIP writes and keep central-directory metadata bounded, with a spool option for very large entry counts. ZIP mutation initially rewrites a new archive; an archive view starts read-only. TAR is naturally sequential; TAR.GZ member lookup generally needs scanning/decompression, unlike a remote ZIP directory. Evaluate `@std/tar` only for its documented profile: the inspected current-main reader is unstable ustar with a numeric-size extension, not demonstrated PAX/GNU/sparse coverage. Recheck the exact release and cancellation/drain costs before selecting it.

CompressionStream supplies codecs, not ZIP records, entry indexes, passwords or encryption formats. Capability-test `deflate-raw` per runtime and expose unsupported codecs honestly. Additional gzip/Brotli/Zstd/XZ/7z/RAR/disk-image profiles need separate codec/format evidence and optional owners. An injected codec must be explicit; no silent whole-file fallback.

Archive admission limits cover directory bytes, entry count, name length, decompressed member bytes, total output, expansion ratio, nested depth, CPU/time, requests and maximum buffered bytes. Reject traversal, absolute/root escape, NULs, duplicate/path-kind collisions and unsupported links/special files before extraction effects. Treat an entry name as virtual path data, not a host path. Fuzz chunk boundaries, truncated records and hostile size fields. Browsers need sandboxed rendering of untrusted HTML/SVG or media at the application layer; archive support does not make active content safe to render.

A partial preview cannot prove a member CRC until the complete entry has been consumed. Report that distinction and keep whole-entry verification separately awaitable. Optional cancellation must retire the decompressor and underlying reader.

Do not add a WebP, PNG, MP3 or MP4 storage driver. Those bytes already fit storage. ZIP/SQL snapshots/Parquet/Zarr/IPLD views interpret structure; image transcoding and media decoding belong to separate consumer capabilities. Format conversion routes must declare losses: file tree to ZIP/TAR, ZIP entry to file, compressed bytes to decoded bytes, and dataset export to files. Arbitrary database, encrypted vault, on-chain record and media conversions are not interchangeable serialization.

## Encryption and vaults

Offer explicit unencrypted content and application-encrypted content modes. TLS, provider-managed encryption, customer-managed cloud keys and client-side payload encryption are distinct. Plaintext mode still uses authenticated HTTPS and available integrity checks. Do not claim a server-side-encrypted object is hidden from the provider.

Use WebCrypto primitives and a reviewed streaming authenticated-encryption format. Evaluate age for interoperable encrypted-file/export use separately from the payload-source spike. The preferred segmented payload design spike is interoperable AES-GCM-HKDF streaming as specified by Tink, implemented with native primitives under the dependency policy, not an imported Tink runtime or a new ad-hoc framing format. Freeze the actual format only after independent review, exact test vectors, cross-implementation decryption and the required random-access/recovery tests. The Tink format is an algorithm/encoding reference; key serialization, associated data and any application manifest still need explicit contracts.

Bound each encryption segment; authenticate it before releasing plaintext. Preserve terminal/truncation checks and distinguish an authenticated selected segment from a fully verified file. Use fresh per-file salt/nonce derivation according to the selected format; never regenerate different plaintext under an already-used key/nonce after an uncertain retry. For resumed writes, retain/reproduce exact ciphertext and transform context or restart with a fresh file identity. Authenticate format version, context and necessary lengths/ordering using the format's rules. Guard index overflow and reject malformed or incompatible parameters.

The caller owns key material and key lookup; do not store raw keys in checkpoints or logs. For the proposed GCM-HKDF format, accept raw input key material or an HKDF CryptoKey with the required derivation usages, or an explicit key-provider derivation capability. A non-extractable AES-GCM CryptoKey cannot be repurposed as HKDF input; do not promise it is compatible. Raw-material/HKDF key-provider integration first; password-based encryption is a separate profile with an approved KDF and parameters, not an improvised password hash. Memory-hard KDF support may require an unavailable primitive and a separate dependency decision. Rotation is rewrite-and-publish with old/new key identifiers and a recovery policy. JS cannot generally guarantee physical memory zeroization; do not promise it.

Content encryption alone leaks names, object count, sizes, timing and access patterns. A filename-hiding vault needs its own authenticated namespace/index and concurrency format. Cryptomator, WNFS, ArFS and other named vault/filesystem formats require exact independent interoperability work. They are not satisfied by putting arbitrary AES bytes into an object.

ZIP password encryption is another format contract. Do not call an externally encrypted ZIP a password-compatible ZIP, and do not write legacy ZipCrypto as the default. Encryption inside ZIP and an encrypted outer archive have different metadata leakage and preview behavior. Defer specialized encrypted ZIP variants until their specifications, licensing, primitives and interoperability are settled; keep unsupported variants visible in inspection.

Compression before encryption is an explicit option, with plaintext/compressed/ciphertext byte metrics. It changes replay and random-access cost and can leak information when secret and attacker-controlled input are compressed together. Do not combine them invisibly.

## Verification and coverage accounting

“Most complete” needs a reproducible comparison, not a backend-name count. Compare dated inventories for OpenDAL, rclone, fsspec, unstorage and the catalog's Visulima reference against the same canonical IDs and operations. They have different programming models and runtimes; report that difference rather than borrowing their support claims. Track named-service coverage, independent protocol coverage, native versus injected/mounted routes, read-only versus writable, runtimes, streaming, crash recovery, encryption, archive views and maintenance freshness separately. Shared-protocol aliases do not become independent protocol implementations.

Use evidence states such as cataloged, contract designed, source implemented, fixture verified, live-service verified and released-artifact verified. Availability/deprecation is a separate axis. A route can be read-verified but write-unverified, or released for Node but unavailable in browsers. Keep exact versions, credential model, service region/configuration, dates, raw reports and excluded capabilities. Do not assert universal support from an emulator, generic S3 endpoint or one happy-path request.

Every family gets success, absence, malformed metadata, permission failure, source/destination races, partial construction, abort, cleanup, one-shot replay refusal and unknown-publication tests. Providers add pagination/continuation, throttling, conditional conflicts, expired credentials and exact final receipts. Read-only views add pre-effect mutation refusal. Streaming tests measure first bytes before EOF, slow sink backpressure, maximum admitted chunk/queue/request concurrency and peak/retained memory with fixed buffers as total input grows. Set budgets in the design before measuring. An upstream producer may allocate an oversized chunk before this library sees it; state that limit honestly.

Archive tests use independent producer/consumer fixtures and fuzz split boundaries, ZIP64, descriptors, encodings, overlaps, malicious names and decompression limits. Crypto tests use independent published vectors and mutation/reordering/truncation cases, key mismatch, nonce boundaries and resume after ambiguous writes. Transfer tests use fresh processes and crashes before/after provider acknowledgement, checkpoint save and final publish; same-process retries are insufficient.

Deno tasks remain command authority. Runtime tests use `--no-check`; static checks run serially in CI under the repository's workstation memory restriction. Maintain real Deno/Node/Bun and applicable browser/Worker lanes, rather than treating shared TypeScript as runtime proof. Add package consumers that import root, one protocol and one optional adapter; inspect the built graph for unused providers/codecs/wallets and execute the exact packed artifact.

CI fixtures and hosted smoke tests use isolated namespaces with explicit cleanup, permissions and cost limits. Do not use ambient production accounts. Emulator-only support is labelled as such until a controlled live run passes. A scheduled secret-backed service matrix may be useful later, but it is a proposed task, not an automation created by this plan.

## First implementation package and decision boundaries

Begin with one vertical proof: native GCS upload/read/list with immutable generation-bound range reads, its object driver/adapter, and checkpoint schema/source-replay design tests. Then demonstrate a process-killed GCS upload resuming correctly and a remote unencrypted ZIP member preview. Reuse that proof to settle the common transfer and archive seams before layering encryption. This sequence makes missing contracts visible before hundreds of services depend on them.

Before publishing a new family, record its maintenance owner, API/spec version, dependency graph, test fixture, service account/permission model, compatibility window, persisted format version, release consumers and deprecation trigger. A protocol that cannot meet the dependency policy, format interoperability or live verification gate remains explicitly constrained; never substitute an empty adapter and mark it done.

Material assumptions: submodules mean optional exports; new dependencies stay within the stated policy; hosted credentials/test budgets will be supplied for live provider proof; encryption key management is caller-owned; complete coverage means every catalog record has an honest disposition, not that every reference/format is a writable backend. These assumptions permit planning now. Optional SDK adoption, native SSH/P2P stacks, encrypted-vault write formats and paid network publication require their own bounded decisions when their implementation slices start.

## Primary sources affecting the design

- [GCS resumable operations](https://docs.cloud.google.com/storage/docs/performing-resumable-uploads) and [retry semantics](https://docs.cloud.google.com/storage/docs/retry-strategy): native sessions, acknowledgement reconciliation and conditional retry ownership.
- [Tus1 protocol](https://tus.io/protocols/resumable-upload): negotiated upload semantics/extensions, separate from filesystem reads and directories.
- [HTTPbis resumable draft](https://datatracker.ietf.org/doc/draft-ietf-httpbis-resumable-upload/): experimental independent protocol; recheck version at implementation time.
- [PKWARE ZIP6.3.10 specification](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT): ZIP framing/ZIP64/format variants; implement from the specification and retain its reference, not redistributed spec text.
- [WebCrypto](https://www.w3.org/TR/webcrypto-1/), [Tink streaming AEAD format](https://developers.google.com/tink/streaming-aead/aes_gcm_hkdf_streaming), [Compression Streams](https://compression.spec.whatwg.org/): native primitives and codecs do not by themselves supply a secure streaming file format or ZIP archive parser.
- [Deno Web APIs](https://docs.deno.com/runtime/reference/web_platform_apis/), [std TAR manifest](https://raw.githubusercontent.com/denoland/std/main/tar/deno.json), [std crypto exports](https://jsr.io/@std/crypto/doc): reuse candidates and explicit runtime/maturity proof requirements.
- [Drive download/export model](https://developers.google.com/workspace/drive/api/guides/manage-downloads), [WebDAV RFC4918](https://www.rfc-editor.org/rfc/rfc4918): file IDs/exports and collection protocols need separate semantics.
- [IPFS trustless gateways](https://specs.ipfs.tech/http-gateways/trustless-gateway/): verified content requires block/DAG-aware verification rather than trusting a downloaded range.
- Comparison sources: [rclone operation matrix](https://rclone.org/overview/), [fsspec features](https://filesystem-spec.readthedocs.io/en/latest/features.html), [OpenDAL](https://opendal.apache.org/), [unstorage drivers](https://unstorage.unjs.io/drivers).
