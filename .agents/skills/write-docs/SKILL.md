# Write docs

## Reading boundary

Minimum: read this entrypoint and the linked shared software-quality contract.
Read resources explicitly marked required for the operation; for long guides,
read the applicable sections before making that decision. Use other references
only when they resolve a decision actually in scope. Do not read an entire tree
or recursively select every companion to prove diligence. Recover truncated
required reads. Stop expanding context when the applicable rules and source
behavior are understood; report any material unavailable guidance.

## Shared obligations and companion selection

Read [software quality](../../guides/software-quality.md) before this capability's work.
Comments, docs, naming, imports, readability and correctness are explicit duties
even when no companion is separately selected. Read the applicable detailed
sources linked there before judging those decisions; recover truncated required
reads. The selected capability and real domain/runtime owners share one plan
and verdict. Read this entrypoint and the shared contract first. Read linked detail only
when its decision is in scope; stop when the applicable contract is understood.
Do not recursively load companion skills or historical material for reassurance.



Read [documentation](../../references/docs.md), [comments](../../references/comments.md) for source/API prose, and [diagram fidelity](../../references/diagrams.md) for diagrams. Use the relevant [plain-English sections](../../guides/writing-technical-docs-in-plain-english-handbook.md) for substantial text. Read [documentation types](references/documentation-types.md) to choose the reader's primary task, shape tutorials/how-to/reference/explanation, connect their navigation and check the result. Infer supplied audience and goals before asking for missing context.

Start from a real complete example or concrete reader problem, then explain contracts and details in useful order. Preserve technical nuance and distinguish implemented facts, proposals and open questions. Follow source exports, callers, errors, ownership and supported runtime before asserting behavior. Comments include important private invariants, not only exports; avoid narrating trivial syntax.

For plans, discovery notes, or progress updates, use
[anchors](../../guides/product/anchors.md) and
[planning](../../guides/product/planning.md). Lead with the customer question,
actual observation, scope, product meaning, and next decision. Keep raw evidence
traceable and preserve unsuccessful or inconclusive results. Research claims
and implementation activity do not become observed product outcomes through
wording. Use exact commands, paths, and metrics only when verified.

Use tutorials for learning, how-to for completing a task, reference for lookup and explanation for reasoning, without stripping essential context just to enforce a category. Name assumptions and unrun steps. Diagrams must show actual state, authority, failures and recovery; label proposed edges. Check examples, commands, local links and navigation. Review the actual result as a reader without the chat. Documentation work does not authorize product behavior changes or live operational commands.
