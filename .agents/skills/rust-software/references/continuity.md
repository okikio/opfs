# Resume from evidence, not remembered conclusions

Read this file before a handoff, context reset, long interruption or final report.
Keep one task record beside the project's established planning records.
Do not create a second system that competes with the repository's authority.

## Record the next decision in a small durable state

Keep these fields current:

1. Customer outcome, acceptance criteria, explicit constraints and authorized mode.
2. Starting repository/branch/full SHA, dirty work and relevant guidance version.
3. Applicable skills and exact reference files actually read.
4. Artifact/host/feature matrix, with each required operation and runtime proof.
5. Known evidence, remaining questions, blocked prerequisites and next probe.
6. Exact changed files/symbols, consumers, generated inputs and implementation plan.
7. Commands and raw results, including failures, timeouts and invalid attempts.
8. Memory ownership, unsafe assumptions, cancellation and cleanup still to verify.
9. Last completed step, current work, next safe command and expected observation.
10. Recoverable source/artifact location and unresolved divergence.

Separate research statements from observed results. Keep exact versions, input
checksums, flags and feature combinations with measurements. Do not replace a
long-running plan with a short handoff that loses earlier unresolved work.

## Re-enter deliberately

On resumption, read this skill's entry point and [contract](contract.md), the
task record, current repository instructions and relevant source. Verify the
working revision and changed state before trusting old evidence. Reload only
the reference topics needed for the next decision. Reopen a conclusion when
the compiler, dependency, feature, host, input or product contract changed.

Short reference files reduce truncation risk; they do not guarantee attention.
Keep critical rules in the entry point and contract, and make required CI jobs
and artifact inventories enforce the mechanical parts. Missing evidence remains
missing even when an agent remembers a prior success.

## Report an anchor that a teammate can use

State the question, observation, evidence/scope and meaning first. Then name the
decision it permits and the next unanswered question. A useful update may say:

> The standalone framing test accepts a terminator after the configured window.
> The original tests still pass. This narrows the problem to deadline checking
> before frame acceptance. The next check is the fix against both late complete
> frames and multiple valid frames in one read. Full worker integration is unrun.

This is an illustrative reporting shape, not permission to claim those facts for
another revision. Never turn implementation activity into product evidence.

Before final delivery, reconcile every requested item and validation row. State
what is complete, what failed and what remains unverified. Validate the exact
archive/package being handed off, including visible skills, guides and handbook.
Use repository recovery rules for patches, bundles and durable research records.

Source: the user's anchor-based product development and cross-chat recovery
requirements. This is a local working policy, not an upstream Rust guarantee.
