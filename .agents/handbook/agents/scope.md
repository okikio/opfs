# Prove a requirement before expanding the design

Trace the requirement to the current user outcome, implementation or supported upstream contract. Distinguish a real need from a copied default, historical workaround or preferred tool.

Compare existing configuration, supported extensions, a published package, an upstream artifact and owned source using the same acceptance criteria. A new maintained layer needs a demonstrated gap, an owner, an upgrade path and the cost of keeping it correct.

Use the least machinery that can answer the next question. A direct function call or existing executable may be enough. Preserve the mechanism being investigated while removing unrelated setup.

If evidence shows a necessary change inside the authorized outcome, update the plan and continue. If it introduces a different product goal, recipient, destination or material constraint, state the exact decision that is missing and keep independent work moving.

Do not narrow scope silently to the easiest component. Trace connected callers, exports, configuration, persisted data and user flows when replacing behavior. A migration is complete only when its intended consumers and obsolete paths have been reconciled.
