# Test the exact requested action

Choose the operation that can establish the user's claim and run it from the relevant consumer. Bind the test to the action, environment, artifact, identity, input and permitted side effects.

A direct probe is useful early. It can isolate a parser, provider call or configuration question without a new framework. Preserve its raw result and limits, then test the connected consumer when claiming an application outcome.

For messages, use the intended action and authorized recipient. For identity work, preserve real accounts and required consent. For content changes, keep intentionally incomplete records intact and verify writes by read-back. For browser changes, inspect the built route and relevant interaction state rather than substituting a successful HTTP response.

Include the changed failure, retry, cancellation or cleanup behavior when it affects the contract. Keep setup failure separate from application failure. If a required interaction or host is unavailable, identify the limit rather than substituting an unrelated successful check.

Use the [acceptance record](../project/acceptance.md) and report what the observation establishes. A screenshot, unit test or health check cannot stand in for behavior outside its scope.
