# From a question to a verified result

The playbook sequences the work. The handbook explains the choices, and the selected skills carry out the engineering. Keep one task record and one evolving plan so a changed assumption updates the work that depends on it.

## Establish the next useful step

| Stage | Action | Evidence that permits the next step |
| --- | --- | --- |
| Understand | Identify the reader or customer, first useful action, intended decision, scope and current source. | A concrete outcome and the consequential unanswered question. |
| Investigate | Inspect current contracts and run the smallest relevant authorized probe. | An observation with inputs, conditions, limits and a next decision. |
| Plan | Trace the real owners, consumers, state and failure paths. Select affected skills. | Verified change locations, acceptance checks, dependencies and bounded assumptions. |
| Implement | Change the owning contract and its affected consumers, examples and configuration. | A reviewable result with obsolete paths reconciled. |
| Verify | Exercise the relevant public entrypoint, built artifact or user journey. | Passed, failed, blocked and unrun checks tied to the exact result. |
| Deliver | Provide the requested artifact and operating instructions. Publish or deploy when authorized and required. | A usable handoff, identified owner and applicable recovery path. |

Discovery and a narrow probe can begin as soon as the intended scope supports them. Substantial implementation needs an explicit question and proof plan. If existing evidence already settles a routine change, proceed with the appropriate check; do not create an experiment merely to fill a record.

After a useful observation, apply the [shared product method](../guides/product/README.md). Record what changed in the team's knowledge, the decision it supports and the remaining question. A failed setup establishes a setup limitation. An inconclusive result leaves the product question open.

## Select the operational branch

Use [intake](procedures/intake.md) when the source, environment or outcome is unfamiliar. Use [service checks](procedures/service-contracts.md) only for dependencies that the task requires. A package or CLI can complete at verified artifact delivery. A change that needs a reviewer environment continues through [preview](procedures/preview.md); authorized production promotion continues through [promotion](procedures/promotion.md).

When a step fails, preserve its evidence and choose the [smallest valid recovery](procedures/recovery.md). Inspect actual state before retrying a mutation. When temporary work ends, follow [retirement](procedures/retirement.md). Update instructions through [procedure maintenance](procedures/maintenance.md) when an incident or changed contract exposes a gap.

During an incident, carry out authorized stabilization and preserve evidence before expanding discovery. During a long task, use [milestones](agents/milestones.md) and [resumption](agents/resume.md) to retain the outcome and current state. Reuse authorization already established for the same action and destination.

## Close the promise made to the reader

A research task can finish with a supported decision or a precise unresolved limit. An implementation task needs evidence for the promised behavior. A compiled artifact, a healthy process and a completed user action support different claims.

Compare the original outcome, latest accepted changes, final artifact and checks. Explain how to use the result, what was verified and what remains unverified. Preserve the next action for anything left open; do not label an unmet required acceptance condition complete.
