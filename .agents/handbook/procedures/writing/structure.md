# Give the procedure one observable outcome

Name the task as an action and say when to use it. Define the starting state and the visible result before listing commands. Include only prerequisites that the operation actually needs, with a way to check them.

A useful procedure contains the outcome, trigger, applicable environment, authority and scope, prerequisites, ordered actions, expected observations, meaningful failure branches, cleanup and the completion record. Keep explanations near the decision that needs them; link deeper reasoning separately.

Distinguish required steps from optional alternatives. If an action depends on first-install, upgrade or recovery state, show the decision before that action. Avoid making the reader discover the distinction after a destructive step.

Use a table when actions, observations and failure responses need direct comparison. Use numbered steps when order is the main concern. Introduce unfamiliar terms and units before using them in instructions.

Keep exact defaults and commands at their owning source. A second procedure can refer to that owner instead of maintaining another executable recipe. A compact entry route should lead to the full procedure without replacing its prerequisites and recovery detail.
