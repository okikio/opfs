# Files in a Cloudflare D1 binding

Inject the database binding from your application to store small files as versioned SQL records. The application owns
binding configuration, database selection, permissions, migrations and lifetime. No Cloudflare package, Worker global or
ambient credential lookup is required:

```ts
import { createFileSystem } from "@okikio/opfs";
import { createD1Adapter } from "@okikio/opfs/adapter/d1";
import type { D1BindingType } from "@okikio/opfs/driver/d1";

export async function note(database: D1BindingType): Promise<Uint8Array> {
  const adapter = await createD1Adapter(database, {
    table: "application_files_v1",
    maxFileBytes: 256 * 1024,
    pageSize: 32,
    maxListEntries: 10_000,
  });
  const fs = createFileSystem(adapter, { coordination: "local" });
  try {
    await fs.writeFile("/notes/a.txt", "hello", { parents: true });
    return await fs.readFile("/notes/a.txt");
  } finally {
    await fs[Symbol.asyncDispose]();
  }
}
```

The adapter creates a record driver and the generic OPFS record projection. `createD1Driver(database, options)` also
works independently when callers need canonical records or driver inspection directly. Both factories borrow the
binding. Disposing the filesystem never closes, drops or deletes the injected database. Factory initialization is
explicit SQL I/O; importing either module does none. D1's
[prepared-statement API](https://developers.cloudflare.com/d1/worker-api/prepared-statements/) owns actual binding and
execution.

## One versioned row per file or directory

The default table is `opfs_d1_v1`. Reserve the configured table and its `<table>_parent_path` index exclusively for this
layout; this is not a projection of arbitrary existing business tables. Table names must satisfy the repository's SQL
identifier rules and contain at most 64 characters. Values always use bound parameters; identifiers are validated and
quoted before SQL preparation.

Each row stores `version`, `path`, `parent_path`, `name`, `kind`, `data`, `size`, `last_modified` and `media_type`. The
canonical path is the primary key. Direct-parent and path form the listing index. `version` is 1. File data is canonical
base64 text with its decoded byte size; directories have null data/media type and zero size. Modification time is a
nonnegative safe integer in Unix milliseconds. The driver validates physical SQL columns, schema version, canonical
path/parent/name agreement, numeric precision and base64 extent before returning a canonical record. It rejects corrupt
rows instead of normalizing them into another logical file.

This deliberately reuses the existing record programming model. It does not wrap db0's SQL backend: that backend's
whole-directory query would materialize all child rows, including payloads. This driver has its own bounded metadata
queries and result confirmation, while the record adapter retains the established filesystem behavior.

`initialize` defaults to true and executes `CREATE TABLE IF NOT EXISTS` followed by `CREATE INDEX IF NOT EXISTS` before
returning. It never detects, migrates or replaces an incompatible table. With `initialize: false`, applications must
install this schema and index before creating the driver; missing or incompatible columns fail when statements are
prepared or executed. Initialization is not an all-or-nothing migration: if index creation fails after table creation,
the table remains. The database owner must repair that schema. No automatic DROP or destructive rollback occurs.

A replacement uses one SQLite UPSERT with eight bound parameters and the literal layout version. That single-row
replacement is atomic under D1's SQL execution contract. It does not supply compare-and-swap or a revision token. The
generic filesystem's append/update and directory operations may span several reads and writes; those operations are
cooperative and are not upgraded into transactions. Local filesystem coordination does not fence other Workers.

## Bounded queries and concurrent changes

Exact get and stat queries use `LIMIT 1`. Stat and direct-child listing select metadata columns only; they do not fetch
or decode base64 file bodies. Listing uses the indexed predicate `parent_path = ? AND path > ?` with
`ORDER BY path
COLLATE BINARY LIMIT ?`. The driver checks strict forward movement using UTF-8 octet comparison, matching
SQLite's BINARY ordering even for non-BMP names. A stored root record is excluded from its own child listing.
JavaScript's UTF-16 string comparison would use a different order for some names and could incorrectly reject a valid
page.

`pageSize` defaults to 64 and admits 1–128 rows per query. `maxListEntries` defaults to 10,000 and admits 0–1,000,000.
After reaching that entry budget, the driver can inspect one extra metadata row to distinguish an exactly full directory
from overflow. It throws on overflow instead of presenting a truncated directory as complete. Consumers can receive
valid earlier rows before that final failure; they must treat iteration failure as incomplete membership. A zero entry
budget permits empty directories and rejects any actual child.

An iterator requests its next page only as the consumer advances. Early return releases the retained page and performs
no later query. A native D1 query already in progress cannot be interrupted: this structural API has no signal or cursor
cancellation method. Higher filesystem layers own caller cancellation, but aborting does not retroactively undo a native
query or mutation.

Keyset pages are separate SQL observations. Concurrent additions before an already visited cursor can be missed;
concurrent changes can alter later pages. A bounded scan is not a snapshot or authoritative complete membership during
concurrent mutation. The caller can inject an application-owned D1 session because it supplies the same `prepare()`
surface; session selection and bookmarks stay with that caller. This driver does not discover a session, select a
replica or assert a stronger consistency contract than the injected binding provides.

## Limits and allocation costs

Driver inspection separates numeric row, parameter and SQL
[D1 provider limits](https://developers.cloudflare.com/d1/platform/limits/) from this implementation and caller policy.
D1 currently documents a 2,000,000-byte row/string/BLOB ceiling, 100 bound parameters per query and 100,000 bytes of SQL
text. It also documents a 50 MB result ceiling; the driver does not infer an exact byte count from that unit spelling.
This driver needs nine columns, eight mutation parameters at most, and short fixed SQL text. D1's per-invocation query
budget still applies, including initialization, facade lookups and every listing page; the driver does not hide or
bypass that budget through undocumented batching.

The implementation admits at most 1 MiB of decoded file bytes. Canonical base64 therefore occupies at most 1,398,104
ASCII bytes before other row fields. `maxFileBytes` can lower that ceiling, including zero for empty files only. A
conservative physical-row accounting budget is 1,500,000 bytes: UTF-8 text fields plus payload text and a 256-byte
allowance for scalar values and row overhead. This is an implementation admission rule, not an assertion that SQLite's
physical pages have that exact size. Paths, parent paths and names each have a 4096 UTF-8-byte budget; media type has
1024 bytes. Unpaired surrogates reject before binding instead of creating replacement-encoded aliases.

SQL pages limit row count and omit payloads before native execution. The binding itself allocates its returned results
before the library can validate their cardinality and field sizes. A malicious structural binding or foreign oversized
row can therefore allocate before rejection; the driver does not claim control over opaque SDK/runtime allocation. The
exclusive table layout and validated library writes establish the normal profile, while returned rows are still checked
defensively.

Files are whole values. Reading a byte range through the filesystem may materialize the complete base64 record and then
decode it. Streaming/range-native access, binary storage, partitioning, native append, multipart continuation and
transactions are not advertised. Files beyond the profile belong in an object/file backend, or in an explicitly designed
partitioned driver with its own visibility and recovery contract.

## Query failures and uncertain writes

All native query results must report `success === true`. A fulfilled Promise does not count as an acknowledgement by
itself. Reads also require the expected bounded results array. `D1Error` retains provider error text when a native
result reports failure. Initialization and read failures reject directly; no failed query is quietly converted into
absence.

Once `run()` has been invoked for replacement or deletion, a thrown result or `success: false` becomes `D1MutationError`
with `outcome: "unknown"`, preserving the original cause. This conservative classification does not pretend that failure
means rollback: an application-owned transport can lose an acknowledgement after SQL commits. Parameter validation and
binding happen before that mutation boundary. The driver never automatically retries a mutation. Reconcile the exact
record and the application's intended state before deciding whether another write is safe; D1 row metadata does not
attribute a write to one attempt or implement idempotency by itself.

## Evidence

`tests/d1.test.ts` runs the SQL against Node's built-in SQLite engine through an authored D1 binding/result wrapper. The
observed independent engine on 2026-11-05 was Node v26.13.0 with SQLite 3.54.0. The fixture proves real SQL execution,
UPSERT and index behavior, Unicode keyset ordering, metadata-only bounded pages, early iterator return, overflow,
canonical record validation, lower file policy, failed native acknowledgements and the full adapter read/write/remove
flow. It also executes SQL successfully before deliberately losing its acknowledgement to check uncertainty handling.
The same focused suite runs under Deno's Node SQLite compatibility API.

This is independent SQL-engine evidence plus authored D1 protocol-envelope evidence. It is not deployed D1 conformance,
Cloudflare replication behavior, quota enforcement, timing, cancellation or performance measurement. No Cloudflare
account, production credential, third-party database package or local provider emulator is required.
