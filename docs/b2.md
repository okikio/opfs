# Native Backblaze B2

Use the native client when you need B2 file IDs and version ownership. This is separate from the S3-compatible B2
endpoint. Supply credentials explicitly and keep the returned authorization token private:

```ts
import { authorizeB2, createB2Client } from "@okikio/opfs/b2";
import { createB2Adapter } from "@okikio/opfs/adapter/b2";
import { createFileSystem } from "@okikio/opfs";

const authorization = await authorizeB2({
  applicationKeyId: "caller-provided-key-id",
  applicationKey: "caller-provided-secret",
  fetch: globalThis.fetch,
});
const client = createB2Client({
  authorization,
  bucketId: "caller-provided-bucket-id",
  fetch: globalThis.fetch,
  subtle: globalThis.crypto.subtle,
  maxUploadBytes: 8 * 1024 * 1024,
});
const fs = createFileSystem(createB2Adapter(client), { coordination: "local" });
try {
  await fs.writeFile("/note.txt", "hello");
  console.log(await fs.readFile("/note.txt"));
} finally {
  await fs[Symbol.asyncDispose]();
}
```

Construction performs no requests. `authorizeB2()` is an explicit v4 authorization call; applications can instead supply
an existing account token with its API and download endpoints. The caller owns secret storage, token rotation, Fetch,
and crypto capabilities. No environment variables, keychains, buckets or default credentials are discovered.
Authorization restrictions remain enforced by B2; the client does not upgrade token permissions. Account authorization
uses [the v4 native authorization contract](https://www.backblaze.com/apidocs/b2-authorize-account).

## Names, snapshots and deletion

A name selects the currently visible file. `head()` resolves one exact name with a bounded prefix listing; a neighboring
name does not count as a match. Metadata exposes `version` and `{ kind: "version", value: fileId }`, preserving the
opaque file ID. It does not invent an ETag. `get()` with that revision retrieves metadata by ID, validates the name and
bucket, then downloads that exact ID. `openObjectSource(driver, key)` therefore keeps reading the captured version even
when another writer replaces the current name. A provider deletion or lifecycle rule can still remove that version.
[Download by ID](https://www.backblaze.com/apidocs/b2-download-file-by-id) preserves this native version selection.

`download(file)` returns a stream whose consumer owns completion or cancellation. It checks the file ID, filename,
status, encoding, Content-Length and exact Content-Range, then checks received bytes through EOF. It rejects encoded
payloads because transparent Fetch decoding cannot preserve stored byte offsets. Partial reads authenticate neither SHA1
nor an entire object; use the encryption source when authenticated preview is required.

Filesystem removal uses a [hide marker](https://www.backblaze.com/apidocs/b2-hide-file). Earlier uploads remain stored
and billable, and existing snapshots can still read them. The account owner must configure retention and lifecycle
policy. The separate native `deleteVersion(file)` permanently removes one ID. Removing the latest version can reveal an
older one, so it is deliberately not used to implement filesystem removal.
[Version deletion](https://www.backblaze.com/apidocs/b2-delete-file-version) can also be refused by Object Lock; the
client does not bypass governance.

## Uploads and concurrency

This profile accepts only materialized byte uploads, capped at 64 MiB by implementation safety policy and optionally
lowered by `maxUploadBytes`. Driver inspection reports the hard implementation upload limit separately from a lower user
policy; these upload ceilings do not cap reads of existing larger versions. It snapshots admitted native bytes, computes
SHA1 with the injected WebCrypto capability, obtains a dedicated upload token, and sends Content-Length and checksum. A
success receipt must match the name, bucket, length and checksum. This is a bounded copy plus hashing cost, not a
streamed or resumable upload. The native protocol requires these
[upload headers](https://www.backblaze.com/apidocs/b2-upload-file); this profile does not use the larger provider upload
allowance as a memory budget.

The account token goes to configured account/download endpoints. Uploads use the service-returned upload URL and its
separate token. HTTPS is required and redirects are refused. Service-returned upload queries remain opaque. Fetch in
browsers can restrict Content-Length; this upload route needs a Fetch implementation that preserves the required header.
An injected Fetch implementation must preserve status, headers, byte streams and abort behavior.

No request retries automatically. A transport loss, HTTP 408 or 5xx, unexpected success status, or invalid/truncated
success receipt after dispatch raises `B2PublicationError` with `outcome: "unknown"`; inspect native versions before
retrying. A later current-name stat cannot prove that a particular lost write succeeded. Cancellation after sending a
write also cannot prove rollback.

B2 native destination compare-and-swap is not implemented. `ifMatch`, `ifNoneMatch` and revision-conditioned writes or
hide operations reject before I/O. The adapter's no-replace behavior is cooperative; use a single writer or external
coordination. Server-side copy, large-file parts, checkpoint recovery, customer-key server encryption and Object Lock
administration are not implemented. File info uploads admit ten lowercase ASCII-named fields (an implementation policy)
and a conservative 2048-byte combined encoded header-line budget. This also supports the object adapter’s directory
markers. The
[native file-info rules](https://www.backblaze.com/docs/cloud-storage-add-file-information-with-the-native-api) define
reserved keys and header limits. Filesystem move uses the object adapter's documented fallbacks and is not atomic.

## Listings and evidence

`list()` returns one bounded page, accepts a slash delimiter and preserves B2's next filename as an opaque cursor.
Callers must pass the same prefix and delimiter when continuing. Control/error bodies use the shared 8 MiB response
ceiling. The object adapter adds independent scan-page and retained-entry budgets. This follows the native
[list-file-names contract](https://www.backblaze.com/apidocs/b2-list-file-names), including its separate folder entries.

`tests/b2.test.ts` checks requests and responses using deterministic Fetch fixtures, a published SHA1 `abc` known
answer, range failures, lost receipts, cancellation, and object-source composition. These tests establish protocol
behavior against authored fixtures. They do not establish real B2 account interoperability, browser upload-header
compatibility, Object Lock behavior, independent emulator conformance, throughput or live resumability. No production
credentials or real-server evidence were available for this slice.
